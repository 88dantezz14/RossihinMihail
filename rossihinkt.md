1. Подключиться снаружи к SSH не выйдет. Правило в iptables просто разрешает трафику пройти через сетевой фильтр на входе. Но дальше ядро пытается передать пакет приложению, которое слушает адрес назначения. Наш SSH слушает только локальный интерфейс 127.0.0.1 и про внешний адрес 203.0.113.10 ничего не знает, поэтому ОС сразу сбрасывает соединение. Nginx при этом слушает 0.0.0.0, то есть принимает пакеты со всех доступных интерфейсов. В итоге привязка сокета решает: если порт на конкретном адресе не слушается, открытый файрвол ничем не поможет.
2. Для выхода в сеть не хватает трех вещей: маршрута по умолчанию (default gateway) внутри web42ns с указанием на IP хостового конца veth, включенной пересылки пакетов на хосте (sysctl net.ipv4.ip_forward = 1) и правила MASQUERADE в iptables. Адрес 10.200.0.2 приватный и не маршрутизируется в интернете, провайдерские роутеры его просто сбросят, да и серверы в сети не смогут ответить на серый IP. Правило MASQUERADE подменяет серый адрес источника на реальный внешний IP хоста при выходе пакета, а на обратном пути возвращает адрес web42ns, позволяя получать ответы.
3. Контейнер находится в отдельном сетевом пространстве со своей подсетью, поэтому трафик к нему идет транзитом. При пробросе порта через флаг -p Docker создает правило DNAT в цепочке PREROUTING, которое срабатывает до маршрутизации и сразу меняет внешний адрес назначения на внутренний IP контейнера. Из-за этого пакет идет не локальному хосту, а в другую сеть, минуя цепочку INPUT и попадая напрямую в FORWARD. Команда ufw deny 8080 по умолчанию блокирует порт в INPUT, где этого трафика уже нет, а правила самого Docker в цепочке FORWARD стоят выше правил ufw и спокойно пропускают пакеты.
4. При прямом открытии порта 8080 ломаются две основные вещи. Во-первых, страдает удобство пользователей: стандартный порт для веба это 80 (или 443 для HTTPS), и без прокси всем придется вручную дописывать :8080 в адресной строке. Во-вторых, теряется нормальная работа с HTTPS и несколькими сайтами: reverse proxy позволяет в одной точке настроить SSL-сертификаты и раскидывать запросы по разным доменам или путям. Без него придется настраивать TLS прямо в приложении web-42, а повесить еще один сервис на этот же порт будет технически невозможно.
